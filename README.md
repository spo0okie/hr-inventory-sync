# SAPsync

Синхронизация кадровых данных по схеме-хабу: кадровые источники (**SAP**, в перспективе 1С) стекаются в инвентаризацию **ARMS**, откуда выбранные организации выгружаются в портал **Bitrix24**.

```
SAP ──────┐
1C (потом)┼──► ARMS (хаб: агрегация, ручное редактирование) ──► Bitrix
ручками ──┘         inventory-arms.php                portal.php
```

Всё общение с ARMS — через его REST API (прямого доступа к БД инвентаризации нет). Прежний механизм прямой синхронизации SAP → Bitrix сохранён в отдельной папке на боевом сервере и в этом репозитории не сопровождается.

Все скрипты запускаются из шелла (обычно по cron) **из корня репозитория** — конфиг и библиотеки подключаются относительными путями.

## Скрипты

### Синхронизация

| Скрипт              | Направление  | Что переносит |
|---------------------|--------------|---------------|
| `inventory-arms.php` | SAP → ARMS  | оргструктура, сотрудники, отсутствия; обратно ARMS → SAP — контакты (email, телефоны) |
| `inventory-arms.php photos` | SAP → ARMS | то же + фотографии (сканы, привязанные к сотруднику) |
| `portal.php`        | ARMS → Bitrix | оргструктура, сотрудники, группы |
| `portal.php photos` | ARMS → Bitrix | то же + фотографии (портрет = последний по дате скан `photo-{pernr}-{дата}`; дата сверяется с `UF_SAP_PHOTO_SYNC`, байты качаются только при расхождении) |
| `portal.php ivanov.i` | ARMS → Bitrix | один пользователь по LOGIN (без прохода по структуре) |
| `portal-absence.php` | ARMS → Bitrix | график отсутствий портала |



Отсутствия вынесены в отдельный скрипт: их десятки тысяч, обновляются они чаще оргструктуры, и держать их в одном прогоне с ней незачем. Запускать **после** `portal.php`: отсутствие привязывается к уже существующему пользователю портала, пользователей эта выгрузка не заводит.

`inventory-arms.php` поднимает только REST-клиент — запускается на любом хосте, видящем API ARMS и кэши SAP. `portal.php` и `portal-absence.php` поднимают фреймворк Bitrix (`prolog_before.php`) — работают только на хосте Bitrix.

### Сервисы портала (не синхронизация, читают только Bitrix)

| Скрипт              | Назначение |
|---------------------|------------|
| `absenceSubscr.php` | «Подписка на отсутствия коллег»: оповещает о приближающихся отсутствиях тех, на кого подписан (`UF_ABSENCE_SUBSCR`) |
| `bDayReminder.php`  | Список именинников на ближайшие 7 дней — в службу персонала |

### Вспомогательное

`dupesCheck.sh` — выборка предупреждений о дубликатах пользователей из лога `/var/log/SAPsync.last`.

## Настройка

Скопируйте `config.sample.php` в `config.php` (он в gitignore) и заполните. В шаблоне указано, какая переменная нужна какому скрипту. Ключевое:

- **`$arms_api`** — URL REST API ARMS (`https://…/web/api`), сервисный пользователь и список организаций (`org_id`) на выгрузку в Bitrix. Пользователю нужны RBAC-права `index/view/update/delete` на `users`, `org-struct`, `absences`, `scans`.
- **`$inventoryOrgs`** — раскладка дерева SAP по юрлицам: `Objid` корня юрлица → `org_id` в ARMS. Организации заводятся в ARMS администраторами заранее, приём их не создаёт.
- **`$dryRun`** — режим сухого прогона (см. ниже).
- **`$sapCache*`** — пути к скриптам обновления JSON-кэшей SAP (вне репозитория).
- **`$sapPushUserData`** — скрипт отправки одного контакта в SAP (вне репозитория): обратная синхронизация email и телефонов из ARMS. Закомментировать, чтобы отключить.

## Выкатка: сухой прогон

Оба пишущих скрипта поддерживают dry-run: при `$dryRun = true` в конфиге они ничего не пишут (в ARMS и Bitrix соответственно), а печатают намеренные изменения строками `[DRY] …` / `[DRY-RUN] …`. Сравнение с существующими записями идёт пачкой и по полям: обновления печатаются с дифом (`поле: 'старое' -> 'новое'`), совпадающие записи не трогаются вовсе (и не считаются изменениями), в конце — сводка `создано / обновлено / без изменений / пропущено`.

Особенности dry-run для фотографий (`inventory-arms.php photos`): бинарники у SAP не запрашиваются — печатается только намерение (`[DRY] upload scans/photo-{pernr}-{date}.jpg`). Пока сотрудники не залиты в ARMS боевым прогоном, фото уходят в счётчик «нет в ARMS» — это нормально: сначала боевой прогон сотрудников, потом режим `photos`.

Порядок выкатки:

1. `$dryRun = true`, запустить `php inventory-arms.php`, изучить лог (что создастся/обновится в ARMS).
2. `$dryRun = false`, залить данные в ARMS, проверить в интерфейсе ARMS.
3. Снова `$dryRun = true`, запустить `php portal.php` на хосте Bitrix, изучить лог. Особое внимание строкам `No ARMS ID - Deactivating` — это пользователи портала, не найденные в ARMS (их деактивирует боевой запуск).
4. `$dryRun = false`, боевой запуск `portal.php`.
5. `$dryRun = true`, запустить `php portal-absence.php`, изучить лог: сколько отсутствий создастся, сколько обновится и — главное — сколько уйдёт под удаление в разделе `Bitrix>ARMS check`. Если под удаление попало больше 20% элементов, скрипт сам откажется удалять и скажет об этом: значит выгрузка ARMS пришла неполной или съехало сопоставление пользователей.
6. `$dryRun = false`, боевой запуск `portal-absence.php`.

Перевод графика отсутствий с легаси-механизма на выгрузку через ARMS существующие элементы не пересоздаёт: ключ сверки (`SAP_ID`) и границы дат сохранены прежними. Обновления получат командировки — их название теперь содержит направление («Командировка в Иркутск (Россия)» вместо «Командировка»).

## Подключение организации с уже заведёнными вручную данными

Если организацию вели в ARMS вручную, а потом она появилась в кадровом источнике (SAP/1С), приём сопоставляет кадровые записи с существующими по цепочке, где **наличие ключа у записи ARMS делает его единственным способом её сматчить**:

| Запись в ARMS | Матчится с кадровой записью |
|---|---|
| есть табельник (`employee_id`) | **только** по табельнику |
| табельника нет, есть uid (md5 СНИЛС/ИНН) | **только** по uid |
| нет ни табельника, ни uid | по ФИО (регистр, е/ё и лишние пробелы не важны) |
| ничего не совпало | создаётся новая запись (дубль) |

Матч по uid/ФИО работает в пределах организации и только при однозначном совпадении: если двое ручных с одинаковым ФИО — не усыновляется ни один, кадровая запись создаётся новой. Усыновление видно в логе строками `[ADOPT] …` и в сводке (`усыновлено ручных N`).

**Подготовка данных перед подключением организации — обязанность подключающего:**

- у ручных записей либо проставить **настоящие** кадровые ключи (табельник, СНИЛС), либо **очистить** поля от выдуманных значений;
- выдуманный табельник опаснее пустого: если он случайно совпадёт с чьим-то настоящим — произойдёт не дубль, а ложное слияние (чужие кадровые данные перезапишут запись);
- если у ручной записи заполнен uid, а в кадровой выгрузке СНИЛС этого человека пуст — матча не будет (ФИО для записи с uid не пробуется);
- ФИО ручных записей должно быть полным и совпадать с кадровым;
- ручная **оргструктура** не усыновляется: кадровые подразделения создаются своими `hr_id`, сотрудники перепривязываются к ним, опустевшие ручные отделы нужно удалить руками. Кто не подготовил данные — разбирает дубли сам.

Первый прогон подключаемой организации обязательно делать с `$dryRun = true` и вычитывать строки `[ADOPT]` — они показывают, кто к кому привяжется.

## Миграция прода с легаси-механизма

Если в БД ARMS оргструктура была заполнена старым механизмом (прямая запись в SQL), она лежит в **другой раскладке полей**: в `id` — Objid узла, в `hr_id` — Objid **родителя** (одинаковый у всех детей), `parent_hr_id` пуст. Новый приём определяет это по дублям `hr_id` в организации и останавливается до первой записи с инструкцией. Конвертация на стороне ARMS — одной командой:

```sql
UPDATE org_struct SET parent_hr_id = hr_id, hr_id = id;
```

Либо очистить `org_struct` — приём пересоздаст структуру с правильными `hr_id`. Таблица `users`, заполненная легаси, конвертации **не требует**: `employee_id` и `Orgeh` (Objid подразделения) совпадают с новой семантикой, связь пользователей с подразделениями оживает после конвертации оргструктуры.

**Секции Bitrix** конвертируются самой синхронизацией: легаси писал в `CODE` голый Objid, новый формат — `{org_id}-{hr_id}`. Поиск секции идёт сначала по новому коду, при промахе — по голому (по соглашению в SAP коды подразделений уникальны между организациями, так что голый код однозначен); найденная легаси-секция переименовывается в новый формат обычным обновлением. Для миграционного прогона `portal.php` в `$arms_api['orgs']` должны быть **ровно те организации, которые выгружал легаси** (иначе пользователи не включённой организации уйдут в деактивацию); новые организации добавлять после того, как коды существующих секций переехали. Секции упразднённых подразделений, которых больше нет в источнике, остаются с легаси-кодами — это безвредно.

## Что выгружается в портал, а что нет

- **Пустые подразделения не создаются**: узел ARMS без активных сотрудников (с учётом вложенных), которого ещё нет в Bitrix, пропускается — ручная оргструктура инвентаризации порталу не нужна. Если в существующей секции портала не осталось сотрудников — она деактивируется.
- **Корневые секции не перемещаются**: их положение (например, под секцией «Организации») синхронизация не сверяет. Новая корневая секция создаётся сразу внутри той же секции-обёртки, где лежат корни остальных организаций — на верхнем уровне Bitrix её создать не даст («В структуре компании должен быть только один раздел верхнего уровня»). Если корней в портале ещё нет, обёрткой считается единственный раздел верхнего уровня; если разделов верхнего уровня не один — секция не создаётся, в логе будет об этом строка.
- **Организация без оргструктуры выгружается одним узлом**: если у организации в ARMS нет ни одного подразделения (данные заведены вручную, структуры нет и не планируется), синхронизация создаёт для неё единственную секцию с названием самой организации (`CODE` = `{org_id}-org`) и ставит в неё всех её сотрудников. У организаций с оргструктурой ничего не меняется: их корень уже представляет юрлицо, второго узла не появляется. Как только в ARMS у такой организации заведут настоящие подразделения, сотрудники переедут в них при ближайшем прогоне, а опустевшую секцию-заглушку нужно убрать из портала руками.
- **Подразделение никогда не очищается**: если подразделение сотрудника определить не удалось (его нет в портале или нет в ARMS), поле `UF_DEPARTMENT` не переписывается — в портале остаётся прежнее значение, а в лог идёт строка «подразделение не определено». Пустое поле выкинуло бы человека из структуры компании.

## Предохранители

Синхронизация деактивирует в портале пользователей, отсутствующих в источнике, поэтому пустая или обрезанная выгрузка опасна:

- `portal.php` и `inventory-arms.php` прерываются, если загружено менее 50 узлов оргструктуры или менее 250 сотрудников;
- приём отсутствий прерывается при менее чем 100 записях в любой из выгрузок (проверяется каждая отдельно: не загрузившийся файл при живых остальных удалил бы свои отсутствия из ARMS обратным проходом);
- `$dryRun` отключает запись целиком.

Контактные данные (email, телефоны) и остальные поля пользователя приходят в Bitrix из **Active Directory**, не из этой синхронизации. Новые пользователи портала также заводятся из AD — синхронизация только корректирует существующих.

**Обратная синхронизация контактов ARMS → SAP** (`inventory-arms.php`, если задан `$sapPushUserData`): email и мобильный ведутся в AD, внутренний номер — в инвентаризации, SAP получает их отсюда. Email отправляется только непустой и при регистронезависимом отличии (пустой email в ARMS не затирает адрес в SAP); телефоны — при любом отличии, включая пустое значение (удаление номера в инвентаризации удаляет его и в SAP). Уволенные пропускаются. В dry-run отправки только логируются (`[DRY] push …`).

## Замечания по данным

- Признак увольнения внутри механизма — булев; значения источников (`X` в SAP, `0/1` в ARMS) трактуются только на границе адаптеров.
- У одного человека может быть несколько трудоустройств (записей с разными табельными). Основное выбирает `getMainEmployment()`: исключает ДГПХ (`Persg` 4), предпочитает неуволенных, берёт наименьший тип.
- Отсутствия: тип нормализуется из кода SAP `Awart` по таблице `CSapAbsentsStructure::$absentsTypes`; неизвестные коды пропускаются, никогда не угадываются. Для командировок из полей `CityTo`/`CountryTo` формируется текст «Командировка в {Город} ({Страна})».
- Отсутствия приходят из нескольких выгрузок SAP: основной (все типы, только утверждённые записи) и плановой (только отпуска, включая ещё не утверждённые). Выгрузки объединяются в одно хранилище по составному ключу, дубли схлопываются; записи основной выгрузки приоритетнее. Незаутверждённый отпуск (в SAP это заблокированная запись инфотипа, `Sprps=X`) принимается с типом `VACATION_PLAN` — «Запланированный отпуск»: даты у него ещё могут сдвинуться. `Awart` при этом не подменяется, поэтому утверждение отпуска обновляет ту же запись ARMS, а не создаёт новую.
- Записи отсутствий с `source=manual` (ручной ввод в ARMS) синхронизация из SAP не трогает. В портал они выгружаются наравне с остальными, с ключом `arms-{id}` в свойстве `SAP_ID`.
- В графике отсутствий портала название элемента — обобщённое («Отпуск», «Болезнь»), а не текст отсутствия из источника: график виден всем сотрудникам. Исключение — командировки, там в названии направление.
- Элементы графика, заведённые в портале руками (без `SAP_ID`), выгрузка не трогает: ни правит, ни удаляет.
