# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Язык

Документация, комментарии в коде и общение с пользователем — на русском. Код и комментарии в этом репозитории написаны по-русски, отвечать пользователю также следует по-русски.

## Обезличивание

ПО изначально писалось под конкретную организацию, затем было переделано в универсальный вариант. **В коде, документации и шаблонах конфигов, попадающих в git, не должно быть упоминаний организации-заказчика** — ни в названиях, ни в доменах, ни в именах переменных и их префиксах, ни в примерах в комментариях.

Реальные названия, домены и учётные данные допустимы только в `config.php` и `config.php.yml` — оба под gitignore по маске `config.php*`. Примеры в комментариях и шаблонах используют вымышленные названия («Рога и копыта», «Табуретка incorporated», «Нуф Нуф и Ко») — держитесь этой линии, добавляя новые примеры.

## Что это такое

Синхронизация кадровых данных по схеме-хабу: **SAP** (в перспективе 1С и ручной ввод) → инвентаризация **ARMS** (агрегация нескольких организаций) → портал **Bitrix24**. Плюс пара сервисов самого портала, к синхронизации не относящихся.

Всё общение с ARMS — через его **REST API** (Yii2-приложение, живёт в отдельном репозитории `C:/Joker/Works/arms`, хорошо документирован — см. его `AGENTS.md`). Прямого доступа к БД инвентаризации в этом репозитории нет.

**Легаси-механизм прямой синхронизации SAP → Bitrix удалён из репозитория** (боевой экземпляр заморожен в отдельной папке на прод-сервере; история — в git до коммита `24f552c`). Не восстанавливайте его части без явной просьбы.

Здесь нет системы сборки, менеджера зависимостей, тестов и автозагрузчика классов. Каждый скрипт в корне — самостоятельная точка входа, запускаемая из шелла (обычно по cron), не через веб. Скрипты подключают `config.php` и `libs/` относительными путями — запускать из корня репозитория.

## Точки входа

| Скрипт | Направление | Что делает |
|---|---|---|
| `inventory-arms.php` | SAP → ARMS | оргструктура, сотрудники, отсутствия (если задан `$sapAbsenceFile`); ключ `photos` — ещё и фотографии |
| `portal.php` | ARMS → Bitrix | оргструктура, сотрудники, группы; аргумент-LOGIN — один пользователь |
| `absenceSubscr.php` | сервис портала | рассылка о приближающихся отсутствиях коллег по подписке `UF_ABSENCE_SUBSCR` |
| `bDayReminder.php` | сервис портала | именинники ближайших 7 дней — в службу персонала (`$bdayRemindMail`) |
| `dupesCheck.sh` | вспомогательный | дубликаты пользователей из лога `/var/log/SAPsync.last` |

`portal.php` и сервисы портала поднимают Bitrix через `prolog_before.php` — работают только на хосте Bitrix (`$bitrix_root`). `inventory-arms.php` фреймворков не поднимает.

Выгрузка отсутствий и фотографий ARMS → Bitrix ещё не написана (следующий этап).

## Архитектура

### Три адаптера

Всё наследуется от [COrgStructureStorage](libs/Abstract/COrgStructureStorage.php) — массива записей в памяти (`$data[id] => [поле => значение]`) с хелперами поиска/сравнения. Поверх него три группы адаптеров:

- **Читатели SAP** (`libs/SAP/`): `CSapOrgStructure`, `CSapUserList`, `CSapAbsentsStructure` — читают JSON-кэши выгрузок SAP, только чтение. `CSapUserList::buildExFields()` добавляет вычисляемые поля (`uid` = md5 от СНИЛС, нормализованный `Uvolen`, `Employ_date`/`Resign_date`). Классы `libs/C1/` — читатели 1С, сохранены под будущее плечо 1С → ARMS.
- **Клиент ARMS** (`libs/Arms/`): `CArmsRestClient` (транспорт: HTTP Basic, пагинация по заголовкам `X-Pagination-*`, multipart-загрузка), `CArmsOrgStructure`/`CArmsUserList` (чтение для выгрузки в Bitrix), `CArmsWriter` (upsert для приёма), `CArmsIngest` (оркестрация приёма: маппинг SAP → ARMS).
- **Сторона Bitrix** (`libs/Bitrix/`): `CBxOrgStructure`, `CBxUserList`, `CBxGroupList` — загружаются через API Bitrix в конструкторе, единственные кто пишет в Bitrix.

`libs/OrgStruct.php` — диспетчер: `initOrgStructure()`/`initUserList()` выбирают класс по `src` дескриптора источника (`sap` / `c1` / `arms`), `loadDataSource()` — загрузчик по `ftype` (`json` / `xml` / `csv` / `rest`).

### Контракт REST API ARMS — критично

- База — `https://<host>/web/api` (именно `/web/api`).
- **Экшн `index` (`GET /{resource}`) отдаёт всё и игнорирует фильтры.** Фильтрация только через `GET /{resource}/filter?поле=знач` (список) и `GET /{resource}/search?…` (одна запись, 404 если нет). `CArmsRestClient::getAll()` с фильтром сам бьёт в `/filter`, `findOne()` — в `/search`.
- Вычисляемые поля (`name`, `fileDate`) отдаются только по `expand=…`.
- Аутентификация HTTP Basic, под RBAC ARMS; сервисному пользователю нужны права `index/view/update/delete` на `users`, `org-struct`, `absences`, `scans`.

### Ключи и идемпотентность

- Подразделение ARMS: `(org_id, hr_id)`; **Bitrix `CODE` = `{org_id}-{hr_id}`** (неймспейс по организации — `hr_id` уникален только внутри юрлица). Единая точка формирования — `CArmsOrgStructure::code()`.
- Сотрудник: ключ записи — `id` ARMS (у одного человека может быть несколько трудоустройств с разными табельными). Upsert приёма — по `(org_id, employee_id)`. Сопоставление Bitrix-пользователя: `XML_ID` (табельный) → `UF_INN` (хеш СНИЛС) → ФИО в обе стороны, всё через `getMainEmployment()` (исключает ДГПХ, предпочитает неуволенных, наименьший `Persg`; при коллизии однофамильцев бросает исключение — пользователь считается ненайденным, не угадывается).
- Усыновление ручных записей на приёме (`CArmsIngest::ingestUsers`): **наличие ключа у записи ARMS делает его единственным способом её сматчить** — запись с табельником матчится только по табельнику, без табельника но с uid — только по uid, совсем без ключей — по ФИО (нормализация: регистр, ё→е, пробелы); матч в пределах организации и только однозначный, иначе создаётся новая запись. Подготовка данных при подключении организации — на подключающем (см. README). Не ослаблять это правило «умным» матчингом.
- Отсутствие: ключ `(source, external_id)`, где `external_id` = `Pernr-Awart-Begda-Endda`. Обратный проход удаляет из ARMS только записи своего источника (`source=sap`), **не трогая `manual`** и другие.
- Фото: скан ARMS с `users_id`, имя `photo-{pernr}-{date}` — SAP-дата фото хранится в имени (поле `fileDate` скана — момент загрузки, не дата фото); сравнение имён — без расширения. Портрет по конвенции ARMS — последнее по дате изображение.

### Раскладка по юрлицам (приём SAP → ARMS)

`$inventoryOrgs` в конфиге: `Objid` корневого узла юрлица в дереве SAP → `org_id` в ARMS. Принадлежность узла/сотрудника определяется подъёмом по дереву (`hasParent`); вне настроенных корней — пропуск; при вложенных юрлицах выигрывает последнее совпадение по списку. Организации в ARMS заводят администраторы, приём их не создаёт. Werks сознательно не используется.

### Нормализации на границах

- Признак увольнения внутри — булев (`isDismissed()`); значения источников (`X`/кириллическая `Х` в SAP, `0/1` в ARMS) трактуются только в адаптерах.
- Типы отсутствий: SAP `Awart` → согласованная таблица `CSapAbsentsStructure::$absentsTypes` → нормализованный код ARMS (`VACATION`…`PERSONAL`, совпадает с `XML_ID` Bitrix) через `CArmsIngest::$absTypeCodes`. Неизвестные коды пропускаются с логом, **никогда не угадываются**. Таблица согласована с кадровой службой — не расширять без решения пользователя.
- Командировки: текст «Командировка в {Город} ({Страна})» из `CityTo`/`CountryTo` (`CArmsIngest::tripComment`), страна из ISO-кода через intl, только если `CityTo` сам не содержит скобок. Продления не различаются, даты в текст не включаются. Текст кладётся в `comment` отсутствия; выгрузка в Bitrix должна использовать его как `NAME` для типа ASSIGNMENT.
- Дата рождения ARMS (`9-02-1984`, д-м-г) → `Gbdat` `Y-m-d` (`CArmsUserList::normalizeBday`).

## Предохранители — не ослаблять

Синхронизация деактивирует пользователей Bitrix, отсутствующих в источнике, поэтому пустой или обрезанный источник массово отключит портал (уже случалось):

- `portal.php` и `inventory-arms.php` прерываются при <50 узлов оргструктуры или <250 сотрудников; приём отсутствий — при <100 записях. Новые источники/загрузчики — проверку количества держать в точке входа.
- `$dryRun` в конфиге: `inventory-arms.php` не пишет в ARMS, `portal.php` не пишет в Bitrix (`readOnly` у объектов хранилищ, пишущие методы логируют намерение `[DRY]`/`[DRY-RUN]`). Порядок выкатки — в [README.md](README.md).
- `COrgStructureStorage::$readOnly` у любого хранилища Bitrix превращает запись в логирование.

## Особенности Bitrix

- Оргструктура — **секции инфоблока** с именем `Подразделения` (поиск по имени, `CBxOrgStructure::getIBlockByName()`).
- Отсутствия — **инфоблок ID 3**, ключ сверки — свойство `SAP_ID`.
- `CBxOrgStructure::cleanParams()` обязательно перед любой записью: Bitrix отдаёт `FIELD` и `~FIELD` плюс `ID`, передача их обратно в `Update()` портит запись.
- Пользовательские поля: `UF_DEPARTMENT` (массив ID секций), `UF_SAP_PHOTO_SYNC` (отметка фото), `UF_INN` (хеш СНИЛС), `UF_ABSENCE_SUBSCR`.
- Пользователи Bitrix заводятся из **Active Directory**; синхронизация только корректирует существующих и пишет `ACTIVE`, `PERSONAL_BIRTHDAY`, `UF_DEPARTMENT`. `WORK_*` и контакты приходят из AD — **не писать**.

## Внешний кэш SAP

Репозиторий не общается с SAP напрямую — через `system()` вызываются скрипты вне репозитория (пути в конфиге), обновляющие JSON-кэши:

- `$sapCache` → `$sapCacheFile` — оргструктура и сотрудники;
- `$sapAbsenceCache` → `$sapAbsenceFile` — отсутствия;
- `$sapPhotoCache <pernr> <файл>` — фото одного сотрудника (JSON: `ArDate` + base64 `OBuffer`, разбирается `CUserPhotoStruct`).

Обратная запись контактов в SAP (`$sapPushUserData` из легаси) в новый механизм не перенесена.

## Два хоста — два диалекта PHP. Критично

- **Хост Bitrix живёт на PHP 5.6.** Всё, что грузится там — `portal.php`, `absenceSubscr.php`, `bDayReminder.php` и их зависимости (`libs/OrgStruct.php`, `libs/Arms/CArmsRestClient.php`, `libs/Arms/CArmsOrgStructure.php`, `libs/Arms/CArmsUserList.php`, `libs/Bitrix/*`, `libs/Abstract/*`) — **только синтаксис 5.6**: без `??`, типов свойств/параметров/возвратов, `fn()`, `match`, короткой деструктуризации `[$a,$b]=`. Короткие массивы `[]`, `list()`, class/array type hints параметров — можно.
- Хост инвентаризации — PHP 8.2: `inventory-arms.php`, `libs/Arms/CArmsWriter.php`, `libs/Arms/CArmsIngest.php`, `libs/SAP/*`, `libs/C1/*` могут использовать современный синтаксис.
- `php -l` локального PHP 8.2 не ловит 7+-синтаксис (он для него валиден) — проверять грепом на паттерны либо линтом на хосте Bitrix.

## Тестовое окружение

- Демо-ARMS: `http://localhost:8081/web/api` (dev, RBAC выключен — работает без авторизации). Данные одноразовые, можно писать при тестах, но убирать за собой. При 500 «table does not exist …_history» — прогнать миграции ARMS (`php yii migrate`).
- Локальный `config.php` может указывать на прод (недоступный с dev-машины) — тесты ходят в демо напрямую, минуя конфиг.
- PHP 8.2 локально; сигнатуры переопределений `loadFrom*` выправлены во всех читателях.
