# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Язык

Документация, комментарии в коде и общение с пользователем — на русском. Код и комментарии в этом репозитории написаны по-русски, отвечать пользователю также следует по-русски.

## Обезличивание

ПО изначально писалось под конкретную организацию, затем было переделано в универсальный вариант. **В коде, документации и шаблонах конфигов, попадающих в git, не должно быть упоминаний организации-заказчика** — ни в названиях, ни в доменах, ни в именах переменных и их префиксах, ни в примерах в комментариях.

Реальные названия, домены и учётные данные допустимы только в `config.php` и `config.php.yml` — оба под gitignore по маске `config.php*`. Примеры в комментариях и шаблонах используют вымышленные названия («Рога и копыта», «Табуретка incorporated», «Нуф Нуф и Ко») — держитесь этой линии, добавляя новые примеры.

## Что это такое

Набор автономных PHP CLI-скриптов, синхронизирующих кадровые данные (оргструктуру, сотрудников, отсутствия, фотографии) между тремя системами: кадровым источником истины (**SAP**, исторически **1C**), внутренней **базой инвентаризации** (MySQL, схема `arms`) и порталом **Bitrix24**. Плюс пара сервисов самого портала, к синхронизации не относящихся.

Здесь нет системы сборки, менеджера зависимостей, тестов и автозагрузчика классов. Каждый скрипт в корне репозитория — самостоятельная точка входа, запускаемая из шелла (как правило, по cron на сервере с Bitrix), но не через веб.

## Точки входа

Скрипты синхронизации:

| Скрипт             | Направление          | Что переносит                |
|--------------------|----------------------|------------------------------|
| `inventory-SAP.php`| SAP → инвентаризация | оргструктура и сотрудники    |
| `inventory-1C.php` | 1С → инвентаризация  | оргструктура и сотрудники    |
| `portal.php`       | SAP → Bitrix         | оргструктура, сотрудники, группы, фотографии |
| `absence.php`      | SAP → Bitrix         | отсутствия                   |
| `absenceC1.php`    | 1С → Bitrix          | отсутствия                   |

Сервисы портала — **не синхронизация**, читают только Bitrix и рассылают почту:

| Скрипт              | Назначение                                                     |
|---------------------|----------------------------------------------------------------|
| `absenceSubscr.php` | Сервис «подписка на отсутствия коллег»: оповещает сотрудников о приближающихся отсутствиях тех, на кого они подписаны (`UF_ABSENCE_SUBSCR`). Ищет отсутствия, начинающиеся послезавтра. |
| `bDayReminder.php`  | Напоминалка о днях рождения: список именинников на ближайшие 7 дней в службу персонала. |

Привязка скрипта к источнику **слабее, чем его имя**: `inventory-*.php` и `portal.php` получают класс хранилища из поля `src` дескриптора источника (`sap` / `c1` / `sql`), так что формально примут любой совместимый источник. Разделение `-SAP` / `-1C` отражает различия в обработке, а не в загрузке: `inventory-SAP.php` дополнительно раскладывает подразделения по юрлицам через `$inventoryOrgs`, пишет хеш СНИЛС (`uid`) и делает обратную запись контактов в SAP; `inventory-1C.php` ничего этого не делает и пишет родителя в колонку `pup`, тогда как `inventory-SAP.php` — в `hr_id`. У `portal.php` есть жёсткая привязка иного рода: он безусловно вызывает `system("$sapCache")` до загрузки, поэтому с не-SAP источником без правок не заработает.

## Запуск скриптов

Скрипты подключают `config.php` и `libs/` **относительными** путями, поэтому запускать их нужно из корня репозитория:

```sh
php portal.php                 # оргструктура и пользователи
php portal.php photos          # то же плюс синхронизация фотографий из SAP
php portal.php ivanov.i        # один пользователь по LOGIN в Bitrix (без прохода по структуре)
php portal.php ivanov.i photos # один пользователь вместе с фотографией
php inventory-SAP.php          # таблицы org_struct и users в базе инвентаризации
php absence.php                # инфоблок 3 Bitrix, сверка в обе стороны
php absenceSubscr.php
php bDayReminder.php
sh  dupesCheck.sh              # выборка предупреждений о дубликатах из /var/log/SAPsync.last
```

`portal.php`, `absence.php`, `absenceC1.php`, `absenceSubscr.php` и `bDayReminder.php` поднимают фреймворк Bitrix через `prolog_before.php`, поэтому работают только на хосте с установленным Bitrix в `$bitrix_root`. `inventory-SAP.php` и `inventory-1C.php` фреймворк не поднимают — они обращаются к MySQL напрямую.

## Конфигурация

`config.php` внесён в gitignore и содержит рабочие учётные данные; `config.sample.php` — шаблон, `config.php.yml` — шаблон для развёртывания. Не коммитьте `config.php` и не переносите его значения в другие файлы.

Конфигурация — это набор глобальных переменных, которые читают точки входа. Ключевая структура — дескриптор **источника данных**:

```php
$dataSrc = [
    'org_id' => 1,                        // идентификатор юрлица в базе инвентаризации
    'org'    => ['src'=>'sap', 'ftype'=>'json', 'path'=>$sapCacheFile],  // оргструктура
    'usr'    => ['src'=>'sap', 'ftype'=>'json', 'path'=>$sapCacheFile],  // сотрудники
    'abs'    => ['src'=>'sap', 'ftype'=>'json', 'path'=>'http://.../sapProxy.php?...'], // отсутствия
];
```

`src` выбирает класс хранилища (`sap` / `c1` / `sql`), `ftype` — загрузчик (`json` / `xml` / `csv` / `sql`). Эти два параметра обрабатываются независимо в [libs/OrgStruct.php](libs/OrgStruct.php): `initOrgStructure()` и `initUserList()` выбирают класс по `src`, затем `loadDataSource()` выбирает метод загрузки по `ftype`.

## Архитектура

### Абстракция хранилища

Всё наследуется от [COrgStructureStorage](libs/Abstract/COrgStructureStorage.php) — массива записей в памяти с ключами (`$data[id] => [поле => значение]`) и хелперами поиска и сравнения. Наследники специализируют его по паре **(система × сущность)**:

| | SAP | 1C | инвентаризация SQL | Bitrix |
|---|---|---|---|---|
| оргструктура | `CSapOrgStructure` | `CC1OrgStructure` | `CSQLOrgStructure` | `CBxOrgStructure` |
| пользователи | `CSapUserList` | `CC1UserList` | `CSQLUserList` | `CBxUserList` |
| отсутствия | `CSapAbsentsStructure` | `CC1AbsentsStructure` | — | — |
| группы | — | — | — | `CBxGroupList` |

Классы со стороны источника (SAP/1C/SQL) грузят данные из файлов или MySQL и работают только на чтение. Классы со стороны Bitrix загружаются через API Bitrix в конструкторе (`CUser::GetList`, `CIBlockSection::GetTreeList`) и являются единственными, кто пишет.

### Контракт синхронизации

Синхронизация — это не движок сравнения диффов. Объекты **связываются друг с другом методами `attach*()`**, после чего каждая запись источника генерирует набор полей, который она ожидает увидеть на стороне Bitrix:

```php
$sapOrg->attachBx($bxOrg);       // источник знает свою цель
$sapUsers->attachBxOrg($bxOrg);  // пользователям нужно дерево подразделений Bitrix для UF_DEPARTMENT
$sapUsers->attachSapOrg($sapOrg);
$bxUsers->attachSap($sapUsers);  // цель знает свой источник
```

Весь путь записи держится на трёх методах, и каждый пишущий класс реализует их одинаково:

- **`bxGenFields($id)`** — сформировать массив полей Bitrix, которые *должны* быть у этой записи.
- **`ckItem($id, $params)`** — сверить текущее состояние с этими полями, залогировать расхождения.
- **`updItem($id, $arFields)`** — записать через API Bitrix, затем перечитать и проверить заново.
- **`correctItem($id, $params)`** — `ckItem(...) || updItem(...)`; идемпотентный вызов «привести к нужному виду».

`CSapOrgStructure::ckBxItemExist()` / `ckBxItemFields()` рекурсивно поднимаются до корня дерева, прежде чем трогать узел, — поэтому отсутствующая цепочка подразделений создаётся сверху вниз. Результаты кэшируются прямо в записи (`bx_item_id`, `checked_bxfields_ok`).

Подразделения сопоставляются по **`CODE` в Bitrix == `Objid` в SAP**. Дерево SAP строится по связям `Pup` → `Seqnr`, а не по `Objid` (см. `getParent()`).

### Сопоставление личностей (пользователь Bitrix → сотрудник SAP)

`CBxUserList::getSapID()` пробует по порядку: `XML_ID` (табельный номер / `Pernr`) → `UF_INN` (md5 от СНИЛС, очищенного до цифр, доступен как вычисляемое поле `uid`) → `Ename` как «Фамилия Имя» → `Ename` как «Имя Фамилия». Поиск по имени использует мягкое сравнение (е/ё считаются одной буквой).

Поскольку один человек может иметь несколько трудоустройств, все поиски идут через `CSapUserList::getMainEmployment()`: метод исключает ДГПХ (`Persg` 4), предпочитает неуволенных и возвращает трудоустройство с наименьшим типом `Persg`. Он бросает `EMPLOYMENTSEARCH_MANY_RESULTS`, когда сталкиваются два основных трудоустройства (однофамильцы); вызывающий код ловит исключение и считает пользователя ненайденным, а не гадает.

### Вычисляемые поля

`CSapUserList::buildExFields()` отрабатывает при загрузке и добавляет производные поля, от которых зависит остальной код: `uid` (хеш СНИЛС), `Employ_date`/`Resign_date` (псевдонимы `DatePrin`/`DateUvol`), нормализованный `Uvolen` (и латинская `X`, и кириллическая `Х` превращаются в `'Уволен'`), `Organization` (разворачивается из `Werks` через словарь `$factories`, подключаемый методом `attachOrgDict()`).

### Внешний кэш SAP

Этот репозиторий не общается с SAP напрямую. Через `system()` он вызывает вспомогательные скрипты за пределами репозитория (пути заданы в конфиге), которые обновляют JSON-кэши, а классы хранилищ их уже читают:

- `$sapCache` (`/opt/SAPcache/portal.php`) → `$sapCacheFile` — оргструктура и сотрудники
- `$sapAbsenceCache` → `$sapAbsenceFile` — отсутствия
- `$sapPhotoCache <pernr> <cache>` → JSON с фотографией одного сотрудника
- `$sapPushUserData <pernr> <type> <value>` — единственная **запись обратно в SAP** (email `0010`, рабочий телефон `0020`, мобильный `CELL`), используется в `inventory-SAP.php`

## Предохранители — не ослаблять

Синхронизация деактивирует пользователей Bitrix, отсутствующих в SAP, поэтому пустой или обрезанный источник массово отключит портал. Защита существует именно для этого случая и уже срабатывала:

- [portal.php:71-74](portal.php:71) прерывает работу, если из SAP загрузилось менее 50 узлов оргструктуры или менее 250 пользователей.
- [absence.php:28](absence.php:28) прерывает работу, если загружено менее 100 записей об отсутствиях.
- `COrgStructureStorage::$readOnly` у любого объекта хранилища превращает `updItem()` в пустышку (`CBxOrgStructure::updItem()` вместо записи логирует намерение).
- `$inventory_import['readonly_mode']` в конфиге заставляет `inventory-SAP.php` печатать SQL вместо его выполнения — используйте это при отладке изменений, пишущих в БД.

Добавляя новый источник или загрузчик, оставляйте проверку количества в точке входа, а не внутри загрузчика.

## Особенности Bitrix, которые стоит знать

- Оргструктура хранится в **секциях инфоблока**, а не в элементах, внутри инфоблока с именем `Подразделения` (ищется по имени через `CBxOrgStructure::getIBlockByName()`, кэшируется в объекте).
- Отсутствия лежат в **инфоблоке с ID 3**, зашитом в `CSapAbsentsStructure::bxGenFields()` и в `absence.php`. Коды типов отсутствия отображаются из `Awart` SAP в ID списка Bitrix через `CSapAbsentsStructure::$absentsTypes`; неизвестные коды пропускаются с записью в лог, но никогда не угадываются.
- У отсутствий нет естественного ключа в SAP — ключом служит составной `Pernr-Awart-Begda-Endda`, он хранится в свойстве `SAP_ID` на стороне Bitrix и используется для сверки в обе стороны.
- `CBxOrgStructure::cleanParams()` обязательно применять перед любой записью: Bitrix возвращает и `FIELD`, и `~FIELD`, плюс `ID`, и передача их обратно в `Update()` портит запись.
- Задействованные пользовательские поля: `UF_DEPARTMENT` (массив ID секций), `UF_SAP_PHOTO_SYNC` (отметка времени фотографии), `UF_INN` (хеш СНИЛС), `UF_ABSENCE_SUBSCR`.
- Новые пользователи портала приходят из **Active Directory**, а не из этой синхронизации. Скрипты только корректируют пользователей, которые уже есть в Bitrix.

## Расхождения absence.php и absenceC1.php

Два скрипта отсутствий делают одно и то же в один и тот же инфоблок 3, но по-разному, и это не случайная разница в стиле:

- **Ключ.** `absence.php` ищет запись по свойству `PROPERTY_SAP_ID`, `absenceC1.php` — по полю `CODE`.
- **Существующие записи.** `absence.php` найденное пропускает не трогая, `absenceC1.php` вызывает `Update()`.
- **Обратный проход.** `absence.php` вычищает из Bitrix отсутствия, которых больше нет в источнике; в `absenceC1.php` этот блок закомментирован.

При объединении скриптов эти различия придётся разрешать осознанно, а не выбирать любое поведение.

## Устаревший код

Часть файлов не запустится в текущем виде. Проверяйте перед тем, как что-то на них строить:

- [absenceC1.php:15-16](absenceC1.php:15) подключает `libs/COrgStructureStorage.php` и `libs/CC1AbsentsStructure.php` — пути до реорганизации `libs/{Abstract,Bitrix,C1,SAP,SQL}/`.
- [absenceC1.php:24](absenceC1.php:24) перебирает `$inventory_import` как плоский список дескрипторов, но в текущем конфиге это словарь с ключами `sources` и `fields`.
- [portal.php:53](portal.php:53) читает источник из переменной `$dataSrc_SAP`, но в конфиге источник назван иначе — имена переменных в PHP регистрозависимы, так что либо на боевом сервере лежит другой конфиг, либо скрипт падает на `validateDataSource()`. Ни `config.sample.php`, ни `config.php.yml` переменную `$dataSrc_SAP` не определяют.

`bDayReminder.php` и `absenceSubscr.php` (сервисы портала) починены: пути подключения выправлены под `libs/{Abstract,Bitrix,SAP}/`, `bDayReminder.php` теперь подключает `config.php` и `CBxUserList`, адрес рассылки задаётся переменной `$bdayRemindMail` (есть в `config.sample.php`, в рабочем `config.php` её нужно проставить).

В заголовках классов SAP стоит предупреждение «не поддерживается в актуальном состоянии» — оно устарело, SAP сейчас является рабочим источником. `inventory-1C.php` и классы хранилищ `c1` сохранены для устаревшего источника 1C.

`inventory-SAP.php` и `inventory-1C.php` собирают SQL конкатенацией значений из источника. Если правите эти файлы, предпочитайте подготовленные выражения вместо развития существующего подхода.
