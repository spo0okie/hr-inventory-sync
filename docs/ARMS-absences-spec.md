# ТЗ: сущность «Отсутствия» в ARMS

Документ описывает новую сущность для проекта **ARMS** (`inventory`), нужную интеграции SAPsync. Реализуется на стороне ARMS; SAPsync выступает потребителем через REST API. Формулировки — в конвенциях ARMS (`ArmsModel`, `ArmsMigration`, автогенерируемый REST, RBAC на класс).

## 1. Зачем

Сейчас отсутствия сотрудников (отпуска, больничные, командировки) синхронизируются напрямую `SAP → Bitrix` (скрипт `absence.php`) и в инвентаризации не хранятся. Проект переходит на схему-хаб: `SAP/1C/ручной ввод → ARMS (агрегация) → Bitrix`. Чтобы отсутствия ходили тем же маршрутом, что оргструктура и сотрудники, в ARMS нужна сущность «Отсутствия», которая:

- **принимает** отсутствия из нескольких источников (SAP, 1C, ручной ввод) с раздельным ключом идемпотентности по источнику;
- отдаёт их наружу через REST **с фильтром по организации** — SAPsync выгружает в Bitrix только выбранные юрлица;
- **не даёт синхронизации из источника затирать записи, введённые вручную** или пришедшие из другого источника.

## 2. Модель данных

Таблица `absences` (создаётся миграцией на базе `app\migrations\arms\ArmsMigration`).

| Поле | Тип (Yii) | Null | Смысл |
|---|---|---|---|
| `id` | `primaryKey()` | нет | ключ |
| `org_id` | `integer()` | нет | юрлицо (как `users.org_id`); по нему SAPsync фильтрует выгрузку в Bitrix |
| `user_id` | `integer()` | нет | FK → `users.id`, конкретное трудоустройство сотрудника |
| `type` | `string(16)` | нет | нормализованный тип отсутствия, см. §3 |
| `date_from` | `date()` | нет | начало периода |
| `date_to` | `date()` | нет | конец периода |
| `comment` | `string(255)` | да | текст отсутствия из источника (SAP `Abstext`) |
| `source` | `string(8)` | нет | источник записи: `sap` \| `c1` \| `manual` |
| `external_id` | `string(64)` | да | натуральный ключ записи в источнике (для `sap`: `Pernr-Awart-Begda-Endda`); для `manual` — NULL |

Плюс стандартные для ARMS поля времени/журналирования (`updated_at` и история изменений через `ArmsModel`).

**Ключи и индексы:**

- уникальный составной `(source, external_id)` — обеспечивает идемпотентный upsert из источника; записи ручного ввода (`external_id IS NULL`) под ограничение не попадают;
- индексы по `org_id`, `user_id`, `(date_from, date_to)` — под фильтрацию выгрузки и поиск пересечений;
- FK `user_id → users.id` (при удалении сотрудника — каскад или запрет, на усмотрение ARMS);
- FK `org_id` — на ту же таблицу юрлиц, что и `users.org_id`.

## 3. Справочник типов

`type` хранит **нормализованное** значение, а не код источника. Значения намеренно совпадают со словарём `XML_ID` типов отсутствия в Bitrix, чтобы выгрузка отображала тип один-в-один без второго словаря:

| `type` | Значение | (ID списка в Bitrix) |
|---|---|---|
| `VACATION` | отпуск ежегодный | 8 |
| `ASSIGNMENT` | командировка | 9 |
| `LEAVESICK` | больничный | 10 |
| `LEAVEMATERNITY` | отпуск декретный | 11 |
| `LEAVEUNPAYED` | отгул / за свой счёт | 12 |
| `UNKNOWN` | прогул | 13 |
| `OTHER` | другое | 14 |
| `PERSONAL` | персональный календарь | 293 |

Маппинг кодов конкретного источника в нормализованный тип (для SAP — коды `Awart`, их группировка сейчас в `CSapAbsentsStructure::$absentsTypes`) остаётся **на стороне приёма в SAPsync**: ARMS про коды SAP не знает и хранит уже нормализованный тип. Неизвестные коды на приёме отбрасываются, в ARMS не попадают.

Реализовать `type` можно ENUM-валидацией в модели или отдельной справочной таблицей `absence_types` — на усмотрение ARMS; для SAPsync важен стабильный строковый код из таблицы выше.

## 4. Соглашения ARMS

- Модель `Absences extends ArmsModel`; при наличии истории — `AbsencesHistory` (как `CompsHistory`).
- Миграция `extends ArmsMigration` (даёт InnoDB + utf8mb4/utf8mb4_unicode_ci, идемпотентное `createTable` с проверкой существования — как в `m200317_..._create_table_schedules`).
- REST-ресурс `/api/absences` появляется автоматически (`BaseRestController` создаёт контроллер для любой модели). Нужно только:
  - задать в REST-контроллере `$searchFields` под фильтры §5 (`org_id`, `user_id`, `source`, диапазон дат);
  - права RBAC на класс: `index-absences`, `view-absences`, `update-absences`, `delete-absences`.
- Ручной ввод: сущность попадает в общий CRUD ARMS. Нужен ли отдельный UI (`views/absences/…`) для ручного заведения отсутствий — решить отдельно (см. §6).

## 5. Что нужно SAPsync от REST API

**Приём `SAP/1C → ARMS`** (запись):

- `GET /api/absences?source=sap&external_id=…` — проверить наличие перед upsert;
- `POST /api/absences` / `PUT /api/absences/{id}` — создать/обновить;
- `GET /api/absences?source=sap&org_id=…` — получить все записи источника в организации для обратного прохода (удаление тех, что исчезли из источника, `DELETE /api/absences/{id}`), **не трогая** `source=manual` и другие источники;
- для привязки нужен `user_id`: SAPsync резолвит его через `GET /api/users?employee_id=…&org_id=…`.

**Выгрузка `ARMS → Bitrix`** (чтение):

- `GET /api/absences?org_id=…` (по списку юрлиц из конфига SAPsync), с полями `user_id`/`employee_id`, `type`, `date_from`, `date_to`, `comment`;
- стабильный идентификатор записи ARMS (`id` либо `source`+`external_id`) кладётся в свойство `SAP_ID` элемента Bitrix и служит ключом сверки в обе стороны.

Сервисному пользователю SAPsync выдать права: `index/view/update/delete-absences` и `index/view-users`.

## 6. Открытые вопросы к реализации в ARMS

- Имя таблицы: `absences` (в этом ТЗ) — подтвердить или выбрать `absents` в стиль SAP-выгрузки `OAbsents`.
- Нужен ли UI ручного ввода отсутствий сразу, или на первом этапе достаточно модели + миграции + REST (ручной ввод — позже)?
- Требуется ли хранить состояние согласования (в Bitrix есть `STATE`/`FINISH_STATE`) — предполагается, что нет; подтвердить.
- Поведение FK `user_id` при удалении/увольнении сотрудника: каскадно удалять отсутствия или сохранять историю.
