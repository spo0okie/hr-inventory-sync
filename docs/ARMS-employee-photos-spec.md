# ТЗ: фотографии сотрудников в ARMS (через сущность scans)

Документ описывает доработку проекта **ARMS** (`inventory`), нужную интеграции SAPsync, чтобы фотографии сотрудников ходили тем же маршрутом-хабом, что оргструктура, сотрудники и отсутствия: `SAP → ARMS → Bitrix`. Реализуется на стороне ARMS. Формулировки — в конвенциях ARMS.

## 1. Зачем

Сейчас фото синхронизируются напрямую `SAP → Bitrix` (`portal.php photos` + `CUserPhotoStruct`): скрипт тянет фото из SAP-кэша (`YfmGetPersPhoto`: base64 + `ArDate`), грузит в `PERSONAL_PHOTO` пользователя Bitrix и пишет отметку времени в `UF_SAP_PHOTO_SYNC`. В инвентаризации фото не хранятся, а в новом (ARMS-хаб) режиме `portal.php` источник — ARMS, и до SAP он не дотягивается.

Идея: хранить фото сотрудника в ARMS как **scan, привязанный к пользователю**, и отдавать в Bitrix из ARMS. Это переиспользует уже готовый механизм scans (файловое хранилище + отметка времени + REST-скачивание + межинстансовая синхронизация).

## 2. Что в scans уже есть (не требует доработки)

- Хранение файла на ФС, поля `file`, `format`, `fileSize`, **`fileDate`** (отметка времени — годится под сверку изменений, аналог `ArDate`/`UF_SAP_PHOTO_SYNC`).
- Поддерживаемые форматы включают `jpg/jpeg/png` — под фото подходит.
- Автогенерация миниатюр (`viewThumb` 512×512, `idxThumb` 160×160) через Imagick.
- REST: `GET /api/scans/download?id=…` (`ScansController::actionDownload`) — отдаёт байты файла.
- Механизм синхронизации файла по timestamp: `Scans::$syncTimestamp='fileDate'`, `Scans::syncFile()`, `SyncController` (синхронизация scans между инстансами уже работает).
- Привязка к сущностям через FK-колонки: `contracts_id`, `techs_id`, `arms_id`, `places_id`, `tech_models_id`, `material_models_id`, `lic_types_id`, `lic_items_id`, `soft_id`.

## 3. Чего не хватает (нужно доработать в ARMS)

1. **Привязки к сотруднику.** В `scans` нет `users_id`. Добавить:
   - миграция на базе `ArmsMigration`: колонка `users_id` (`integer` null) + индекс + FK на `users.id`;
   - в модели `Scans`: запись в `attributeData()` для `users_id`, связь `getUser()`, включение `users` в список объектов-владельцев скана (по образцу `techs_id`/`arms_id`).
2. **Признак «это портрет».** У сотрудника может быть ≤1 фото для портала, но теоретически к пользователю можно прикрепить и другие изображения. Нужен способ однозначно выбрать портрет: либо флаг (напр. `is_portrait`), либо соглашение «единственный скан-изображение у пользователя = портрет». Решение — за ARMS; для SAPsync важно детерминированно получать один портрет на сотрудника.
3. **REST под приём и выборку:**
   - `ScansController::actionUpload` сейчас принимает только `contracts_id` — добавить `users_id` (и `is_portrait`, если выберете флаг);
   - `ScansController::$searchFields` — разрешить фильтр по `users_id` (чтобы выгрузка тянула фото по сотруднику);
   - `actionDownload` — уже есть, доработок не требует;
   - права RBAC сервисному пользователю SAPsync: `index/view/update-scans`, скачивание.

## 4. Как это использует SAPsync

**Приём `SAP → ARMS`** (когда приём переведём на API): для сотрудника с фото в SAP (`YfmGetPersPhoto` → base64 + `ArDate`) — загрузить/обновить scan, привязанный к `users_id`, с `fileDate = ArDate` (чтобы работала сверка изменений).

**Выгрузка `ARMS → Bitrix`**: получить портрет сотрудника (`GET /api/scans?users_id=…` с признаком портрета) и его `fileDate`; если `fileDate` не совпал с `UF_SAP_PHOTO_SYNC` в Bitrix — скачать байты (`GET /api/scans/download?id=…`), записать в `PERSONAL_PHOTO`, проставить `UF_SAP_PHOTO_SYNC = fileDate`. Это заменяет текущий путь `CUserPhotoStruct` (из SAP-кэша) на путь из ARMS-scan.

## 5. Открытые вопросы к реализации в ARMS

- Способ пометки портрета: отдельный флаг `is_portrait` или соглашение «один скан-изображение = портрет»? (Влияет на API-фильтр.)
- Нужен ли отдельный размер/кроп под портал, или отдаём оригинал (портал сам ресайзит, как сейчас с фото из SAP)?
- Ограничение «один портрет на сотрудника» — на уровне БД/валидации или на уровне соглашения приёма?
- Нужен ли UI загрузки фото сотрудника со страницы users (ручной источник), или на первом этапе достаточно приёма из SAP + API.
